# Вопросы жюри и короткие ответы

Короткие ответы для защиты Dependency & License Inspector MCP.

## 1. Что даёт MCP для интеграции?

Совместимый клиент узнаёт, какие инструменты есть у сервера и какие параметры они принимают. Один контракт используется в редакторе и в MCP Inspector, где можно вручную повторить вызов.

## 2. Какой рабочий сценарий вы закрываете?

Разработчик указывает проект и получает список пакетов из манифестов. Дальше можно проверить лицензии и уязвимости, применить политику или экспортировать SBOM. MCP-клиент показывает структурированный ответ или передаёт его следующему инструменту. [Сценарий демо](../DEMO.md)

## 3. Какие инструменты есть сейчас?

Сервер предоставляет шесть инструментов. `analyze_project_dependencies` собирает список пакетов. `scan_vulnerabilities` и `scan_licenses` проверяют риски, `check_policy_compliance` применяет правила, `generate_sbom` экспортирует список компонентов, а `suggest_dependency_replacements` показывает примеры замен.

## 4. Почему Python?

В Python удобно разбирать JSON, YAML и TOML и проверять входные данные через Pydantic. Парсеры и правила можно проверять отдельно от MCP-клиента.

## 5. Что означает «детерминированное ядро»?

Правила дают воспроизводимое решение для заданного набора пакетов, сведений о лицензиях и уязвимостях. При сравнении двух отчётов учитывайте изменения данных OSV и служебные поля SBOM, например время генерации и UUID.

## 6. Зачем исключать LLM из сервера?

Решение о нарушении принимает код по явным правилам, поэтому можно написать тест с ожидаемым результатом. Модель на стороне клиента выбирает инструмент и объясняет ответ. Для самого сервера ключ к модели не нужен.

## 7. Что именно поддерживается из экосистем?

Текущий сканер работает с npm и Python. Он ищет `package.json`, `package-lock.json`, `pnpm-lock.yaml`, `requirements.txt`, `pyproject.toml` и `poetry.lock`. Отчёт охватывает зависимости, которые удалось извлечь из этих файлов.

## 8. Можно ли доверять результату сканирования уязвимостей в демо?

В обычном режиме сервер обращается к OSV. `DEMO_MODE=true` включает демонстрационные данные. При сбое OSV клиент видит статус `unavailable`, а проверка политики отмечает аудит как неполный.

## 9. Как задаётся и проверяется политика?

В `policy_path` передаётся путь к YAML/JSON-файлу, а в `policy` можно передать объект с правилами лицензий и порогами CVE. Сервер проверяет явно указанный файл до сканирования. При настроенном `ALLOWED_BASE_PATH` канонические пути к проекту и файлу политики должны находиться в разрешённой директории. Ошибка чтения или разбора политики останавливает аудит.

## 10. Какие ограничения защищают чтение файлов?

Перед разбором манифеста сервер проверяет `MAX_MANIFEST_FILE_BYTES`. Предел по умолчанию составляет 5 МиБ на файл. При превышении клиент получает имя файла и размер лимита. Отдельные настройки ограничивают длину путей, список исключаемых директорий и размер политики, переданной объектом.

## 11. Что произойдёт при ошибке в списке пакетов?

`scan_licenses` проверяет каждый элемент переданного списка. Пустое или отсутствующее `name` и недопустимое значение `ecosystem` останавливают проверку с указанием индекса и поля. Для опущенного `ecosystem` используется `unknown`.

## 12. Какие форматы SBOM выдаются?

`generate_sbom` сканирует манифесты проекта и выдаёт перечень найденных компонентов в SPDX 2.3 или CycloneDX 1.5 JSON. Формат выбирают по требованиям инструмента, который будет читать SBOM.

## 13. Как работают рекомендации замен?

`suggest_dependency_replacements` возвращает примеры из встроенного списка и в обычном, и в демонстрационном режиме. Результат помечен `demo_mode=true`. Перед заменой команда проверяет совместимость, лицензию и актуальное состояние пакета.

## 14. Насколько большой проект можно сканировать?

Для монорепозитория можно проверять подпроекты по отдельности и исключать служебные директории через `exclude_dirs`. Предел на один манифест настраивается. Скорость и полноту проверки на большом проекте следует оценивать на его собственных файлах.

## 15. Как сервер встраивается в существующую команду?

Разработчик запускает проверку в редакторе перед PR. AppSec задаёт общую политику, чтобы команда проверяла одни и те же правила. Сохранённый JSON можно передать на ревью вместе с результатами других проверок.

## 16. Чем решение отличается от Dependabot, Snyk и GitHub Advanced Security?

Ценность этого проекта в том, что разработчик может запросить локальную проверку лицензий, политики и SBOM из MCP-клиента. В команде, где Dependabot открывает PR с обновлениями, инспектор можно использовать для ручной проверки перед ревью. Более широкий аудит остаётся частью существующего процесса команды.

## 17. Можно ли использовать его в CI?

CI может запустить сервер, вызвать инструменты через MCP-клиент и сохранить JSON или SBOM как артефакт. Команде понадобится собственный шаг интеграции, который учитывает `vulnerability_scan_status` вместе с `compliant`. Пороги CVE применяются к тем записям, для которых известна серьёзность.

## 18. Что в проекте проверялось вручную, кроме unit-тестов?

В Inspector открывали ресурсы и вызывали инструменты на демопроекте. Так нашли два несовпадения формата. Ресурс возвращал словарь вместо строки JSON, а список замен однажды пришёл во вложенном массиве. [Быстрый старт](../README.md#быстрый-старт) · [Демо](../DEMO.md)

## 19. Что улучшили бы первым?

Проверили бы покрытие на манифестах реального пилотного проекта. Сравнение с уже используемым сканером покажет, каких версий и сведений о лицензиях не хватает для решения перед выпуском.
